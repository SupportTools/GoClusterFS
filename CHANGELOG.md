## [Unreleased]

### Upgrade notes

- Volumes this version formats carry the `RequiredProjectQuotas` flag and a project quota table, and older builds refuse them with `unknown required flags 0x200`. Add the table to a volume an older build formatted with `goclusterfs-fsck -enable-quotas DEVICE`, with every node stopped; older builds then refuse it too. Quotas themselves arrive in later changes.
- A node now refuses to mount a volume without storage fencing while another node has it mounted, and tells you which slots hold the other nodes. Under QEMU a paused VM's clocks do not count the pause, so on an unfenced volume a VM paused past its takeover resumed and overwrote file data after a peer replayed its journal, in 6 of 6 test runs, and `goclusterfs-fsck` found nothing. Format multi-node volumes on a device with SCSI-3 or NVMe persistent reservations. To keep running several nodes on an unfenced volume, as on files or virtio disks, pass `-unsafe-allow-unfenced` on every node that joins. A node mounted alone is unchanged.
- The default broadcast ports moved from UDP 31337 and 31338 to UDP 24730 (`-mcast-port`) and 24731 (`-unicast-port`), out of Kubernetes' NodePort range 30000-32767, where kube-proxy can send their traffic to a service. Open the new ports in your firewall, or pass `-mcast-port 31337 -unicast-port 31338` on every node to keep the old ones.
- The on-disk format is now version 3. Mount refuses devices formatted by earlier builds. Version 1 kept one journal for all nodes. Version 2 had room for 4096 inodes, and on devices over 128 GB its refcounts overwrote the snapshot registry and then data blocks. Copy the data off with the old build, reformat with `-format`, and copy it back.
- Devices must be at least 327 MB: the layout reserves 256 MB for 64 node journals of 4 MB and 64 MB for lock records.
- Mount also refuses version 3 devices formatted before lock records had one claim slot per node, before each lock type had its own lock records, or before reads and writes took file I/O locks. Older builds refuse devices this version formats. Copy the data off with the build that formatted them and reformat.
- Volumes this version formats carry the `RequiredSymlinks` and `RequiredFileIOLocks` flags. Older builds refuse them with `unknown required flags 0x40`, or `0x60` before symlinks, or `0x70` before per-type lock records. On version 3 volumes formatted before symlinks but after file I/O locks, creating a symlink returns EOPNOTSUPP; reformat to use symlinks.
- Volumes formatted on a device with persistent reservations carry the `RequiredReservations` flag, and older builds refuse them with `unknown required flags 0x80`.
- Upgrade all nodes together: unmount on every node, upgrade, then mount again. Don't mount one shared device with a mix of old and new binaries.
  - Older binaries reset an inode's generation counters to 0 when they free it, so other nodes can serve stale data after the inode number is reused.
  - Older binaries zero the extent-tree generation (inode bytes 188–195) when they rewrite an inode. Newer binaries then cannot read that file if it has more than two extents, because such files use an extent tree.
  - Directory entries now fill all 4 KB chunks of a directory block. When an older binary removes the first entry of a later chunk, it grows the last entry of the chunk before it across the boundary. This version then stops listing that entry, and fsck reports the directory block.
  - Older binaries read a newer node's waiting mark in a lock record as a held lock.
  - Older binaries free a file unlinked while open at once, even when a newer node still has it open.
  - Older binaries cannot replay a journal this version wrote, because they do not know its link-drop records. After a crash, let this version replay the journal before you downgrade.
  - Older binaries skip rename records when they replay a journal this version wrote, but still apply the replaced file's link drop, which can free a file whose name remains. Upgrade every node before anyone renames.
  - Older binaries roll back, when they mount, a snapshot that a newer node is still creating, and that snapshot then fails with EAGAIN.
- Run `goclusterfs-fsck -repair` before the first mount after upgrading an image that has snapshots or clones. Unmount the device on every node first.
- Older versions marked a file's blocks shared, on snapshot or clone, without counting the owners. Until `goclusterfs-fsck -repair` counts them, this version never frees such blocks, so deleting those files leaks their space, and it refuses to snapshot or clone them (`ENOTSUP`). In-place writes to an old clone still change its source.
- Snapshots now record the birth generation of the file they were taken of, so a later file that reuses the inode number cannot list, clone or delete them. Snapshots older versions made do not record it, and some captured no data, so after the upgrade they are orphans: `getfattr -n user.snapshots` no longer lists them, `GET /api/v1/snapshots` lists them with `orphan: true`, and `DELETE /api/v1/snapshots/<name>` without `path` deletes them. Older binaries keep the birth generation in inode bytes 196–203 only while they do not rewrite the inode, so upgrade all nodes together.
- Earlier versions never stored the setuid, setgid and sticky bits, so existing files and directories have none. Before you mount with `-allow-other`, check the modes of existing files: until now only the mounting user could reach them, and a file with mode 0644 becomes readable by every user. See [Users Other Than Root](docs/DEPLOYMENT.md#users-other-than-root).
- `-skip-recovery` now takes the slot number from the recovery error, as `-skip-recovery=N`, and discards a journal only when the mount takes slot N. A bare `-skip-recovery` is a usage error.

### Added

- `goclusterfs-mount -format -block-size N` formats a volume with N-byte data blocks, a power of two from 8 KB to 1 MB; the default stays 1 MB. Small blocks suit volumes of many small files: a 316 MB node_modules tree takes 0.6 GB at 8 KB blocks and 44 GB at 1 MB. With smaller blocks `-bytes-per-inode` defaults to max(2 × block size, 16 KB) instead of 1 MB. Each extent lock covers 1 MB of the data region whatever the block size, so a write claims no more of them at small blocks than at 1 MB; at 1 MB blocks the lock keys are unchanged. Builds without this refuse such a volume ("superblock layout is not supported by this version: block size N").
- An empty directory gets a project quota with `setfattr -n trusted.goclusterfs.quota -v "bytes=N inodes=N" DIR`, which needs CAP_SYS_ADMIN, and `getfattr` reads its project and limits. Files, directories and symlinks made under it join the project, and links, renames and clones into or out of it fail with EXDEV. Usage is not counted or enforced yet.
- After it joins, a node warns about reservation keys that no registry slot owns, and `goclusterfs_fencing_stale_keys` (`stale_reservation_keys` in the node stats) gives their number. On LIO, such a key's registration can hold the reservation and keep its host writing after a peer revokes that host's later key. Remove them with `goclusterfs-fsck -clear-reservations` once every node is stopped.
- Cache invalidations now reach peers where the network drops multicast, as AWS, Azure and GCP VPCs do. Before, a node learned unicast peers only from multicast it received, and it never used unicast while its multicast sends succeeded locally, so in those networks no invalidation arrived and peers saw changes only after `-cache-ttl`. Each node now writes the address peers can send it unicast to in its registry slot, in bytes older builds treat as unused orphan-list space. While a node lists more than 483 files unlinked while open, its slot holds no address; peers keep the last one they read until the list shrinks and the node writes it again. A node that hears no multicast from a peer for 3 `-broadcast-heartbeat` intervals asks that peer to also send it everything by unicast. `-advertise-addr` sets the address when the default, taken from the route to `-mcast-group`, is wrong, such as behind NAT. Where multicast works nodes still send only multicast.
- `-allow-other` lets users other than the one that mounted use the filesystem, which Kubernetes pods that do not run as root need. The kernel checks each file's owner, group and mode bits (`allow_other` and `default_permissions`). It is off by default, because it changes who can read existing files. A clone by a user other than root now needs read access to the file and write access to the root directory, and the clone belongs to that user. See [Users Other Than Root](docs/DEPLOYMENT.md#users-other-than-root).
- Storage fencing on devices with SCSI-3 or NVMe persistent reservations: each node registers its own key, and before a node acts on another node's death, it removes that node's key, so the device refuses the dead node's writes. `-format -fencing=auto` (the default) turns it on when the device supports it; `-require-fencing` refuses to mount an unfenced volume. `/health` reports it as the `fencing` check, and `goclusterfs-fsck` removes a node's key before `-repair` or `-release-slot` writes over it. `goclusterfs-fsck -clear-reservations -confirm` is the emergency reset: once no node runs, it removes every key and the reservation. A partition formats unfenced, because a reservation covers the whole disk. See Storage Fencing in OPERATIONS.
- Hard links for regular files: `link(2)` gives a file another name, up to 65,000. Directories and symlinks get `EPERM`, and a file with no link left gets `ENOENT`. The journal records the added link, and `goclusterfs-fsck` checks each regular file's link count against its names; `-repair` sets it to the names it finds.
- Symlinks: `ln -s`, `readlink`, `lstat`, `lchown` and `touch -h`. A target of up to 92 bytes is kept in the inode, a longer one, up to 4095 bytes, in one data block. Creating a link is one journal transaction, so a crash leaves either no name or the whole target. fsck checks symlink inodes, targets and entry types and reports bad ones without repairing them. Snapshots and clones of a symlink are refused, as the kernel refuses user xattrs on symlinks.
- `goclusterfs-mount`: a FUSE filesystem that several Linux nodes can mount from one shared block device.
- `-format` sizes the block bitmap, refcount table and inode table from the device. `-bytes-per-inode` sets the inode count (default one per MB of device, 4096 to 16,777,216).
- `O_DIRECT` device I/O, split into shards so requests can run in parallel.
- Distributed locks on the shared device for block allocation, inode updates, directory changes, and file reads and writes. Each node writes its claim into its own slot of a lock record and then reads the record, so two nodes cannot both take a write lock however slow the storage is.
- File I/O locks: each read request takes its file's lock shared and each write, truncate and `fallocate` takes it exclusive, on every node, so a read request never returns part of a write request from any node. Writes to one file from several nodes now run one at a time. A node waiting to write goes before new readers for up to 500 ms. Reads through the page cache can still mix cached pages with newer data until the next open or attribute refresh; OPERATIONS.md has the details and the costs.
- `-direct-io` sends every read and write of file data to the filesystem instead of the kernel page cache, so a `read()` of up to 1 MB never mixes two writes. A shared `mmap` of a file fails with it.
- Each node records its lock record layout in its registry slot, and mount refuses to join while a live node's slot shows another layout, naming that node.
- Write-ahead journal with batch commits and a recovery check on mount.
- Intent logging for multi-step operations.
- Inode cache with generation-based coherency checks, and an extent cache.
- UDP multicast cache invalidation between nodes, with optional HMAC authentication (`-broadcast-secret`).
- Batched TRIM of freed blocks (`-trim`).
- SFB containers for files under 64 KB, disabled: every file uses normal extents and `-sfb` has no effect. A file that an older build stored in an SFB slot stays readable, moves to a full block on its next write or truncate, and frees its slot when deleted.
- Experimental: file snapshots and writable clones through `user.snapshot*` and `user.clone` extended attributes. Read a snapshot by cloning it with `user.snapshot.clone`.
- `goclusterfs-fsck` consistency checker. `-repair` rebuilds block refcounts from every file, snapshot and clone. It refuses to run while the device is in use, and `-repair -dry-run` shows what it would change. Exit codes follow fsck(8): `0` no errors, `1` repaired, `4` errors remain, `8` failed or refused, `16` usage error.
- Benchmark suite (`tests/benchmark`) and an `internal/metrics` package.
- Per-node block reserves (`-block-reserve`, default 64): each node takes a batch of free blocks under one hold of the bitmap lock and hands them to its writes without it, gives unused ones back when idle, at unmount and when space runs low, and waits up to 12 seconds for other nodes' reserves before reporting `ENOSPC`. Journal replay and fsck return the unused reserve of a crashed node. See OPERATIONS.md.
- `/metrics` and `/api/v1/stats/lock` report, per lock type, the acquires served, the acquires that found the lock taken, and how long those waited (`goclusterfs_lock_acquires_total`, `goclusterfs_lock_blocked_total`, `goclusterfs_lock_wait_seconds_total`).
- Go, Docker, and QEMU VM test suites, with `tests/test-manifest.yaml` and `make test-parity` to track coverage across them.
- Fuzz tests for the on-disk decoders (superblock, inode, snapshot descriptor, journal superblock and records, lock records, node registry slots, refcount sectors, directory blocks, extent tree nodes, SFB containers), the journal recovery scan, journal replay checked by fsck, and the HTTP API write endpoints and file paths, with seed corpora from two-hour runs.
- CI gates: unit tests with the race detector and coverage, golangci-lint (`make lint`), govulncheck (`make vuln`), and a `go mod tidy` check.
- Release workflow: pushing a `v*` tag publishes a GitHub Release with `linux/amd64` and `linux/arm64` archives, checksums, and the matching `CHANGELOG.md` section. `scripts/dist.sh` builds the same archives locally.
- `goclusterfs-fsck -version` prints the release version, commit, and commit date.
- `goclusterfs-fsck -release-slot N` also runs while other nodes have the filesystem mounted, when releasing loses nothing: the slot's journal was never used, is clean, or holds no committed transaction. It watches the slot unchanged for 40 seconds first (70 for a slot another node was replaying), and never replays. For a journal with committed transactions or one it cannot read, it refuses and names the steps to stop the cluster, release, and run `-repair`. `-skip-recovery=N` refuses the same way on a mounted cluster, before it registers, and refuses a slot number past the last slot.
- `goclusterfs-fsck -release-slot N -salvage` replays a dead node's journal offline until a transaction fails to apply, then discards the rest, resets the journal and frees the slot. `-release-slot` without `-salvage` or `-discard-journal` lists the journal's transactions and writes nothing, and `-report FILE` keeps a record of what the release did with each one.
- `goclusterfs-fsck -inspect-slot N` describes registry slot N and lists every transaction a replay of its journal would apply, with the inodes and blocks each one touches. It writes nothing, so it runs on a mounted device.
- HTTP API in `goclusterfs-mount` (`-api`, on by default): `/health`, `/metrics`, `/api/v1/status` and `/api/v1/stats/...`. It listens on `127.0.0.1:8080` (`-api-addr`). Mount refuses a non-loopback `-api-addr` or `-api-cors '*'` without `-api-token`, and checks the API flags before it opens the device. `/metrics` uses the Prometheus client library and adds Go runtime and process metrics. `-api-rate-limit` limits requests per client IP (off by default).
- `-api-token-file` (mode 0600 or stricter) and `GOCLUSTERFS_API_TOKEN` for the API token. Mount warns when it comes from `-api-token`, which `ps` shows to every local user.
- HTTP API write endpoints, only with a token: create, list, clone and delete snapshots, clone files, and flush the journal, flush TRIM or clear caches on this node. Snapshot and clone requests run the same code as `setfattr` inside the mount daemon.
- `gfsctl`, a read-only CLI for the HTTP API: `status`, `health`, `stats`, `metrics` and `snapshots`, with watch mode and JSON output. Release archives include it. `gfsctl snapshots` lists every snapshot with orphans marked, and needs the API token.
- Web dashboard at `/ui/` on the API server (`-dashboard`, on by default): status, capacity, cache, journal, TRIM and lock counters, the node registry, and per-file snapshots and clones. Release archives include it; `make dashboard build` builds it from source.
- `goclusterfs-mount -version`, which prints the same version string as `goclusterfs-fsck -version`. `/api/v1/status` reports it too.
- Mount logs a `WARNING` line at startup when `-broadcast` is on without `-broadcast-secret`.
- Design, deployment, operations, and troubleshooting docs in `docs/`.
- Apache License 2.0.
- `goclusterfs-mount` writes every goroutine's stack to its log on SIGUSR1 and keeps running, so a hung call can be traced without stopping the mount.
- A shutdown step that takes longer than 2 seconds logs its name and duration, and a shutdown still running after 8 seconds logs every goroutine's stack.

- `-cache-inodes`, `-cache-extents`, `-cache-negative` and `-broadcast-max-peers` set the cache and broadcast table sizes, and `/metrics` reports each limit next to its size.
- `/metrics` counts what operators need when things go wrong: lock acquires that gave up (`goclusterfs_lock_failures_total`), this node's heartbeat age, crashed nodes' journals it replayed or failed to replay, the transactions it replayed or discarded at mount, registered nodes by state (`goclusterfs_cluster_nodes`), and API responses by route and status code (`goclusterfs_api_requests_total`). `/health` gains a `heartbeat` check that reports degraded when heartbeats run late, before the node would stop.
- A node that hears no broadcasts from a node the registry shows mounted, for 3 `-broadcast-heartbeat` intervals (90 seconds by default), logs a warning naming it, reports `broadcast-peers` as degraded on `/health`, and counts it in `goclusterfs_broadcast_silent_peers`. A network that silently drops multicast was invisible before.
- Rename of files and directories, in one directory or between two, with `RENAME_NOREPLACE`. A rename over a file or an empty directory replaces it; a file another node has open stays readable there until its last close. `RENAME_EXCHANGE` and `RENAME_WHITEOUT` fail with `EINVAL`.
- `goclusterfs-fsck` checks the directory tree: a directory with more than one name, a `..` that does not name the directory that names it, a directory link count other than 2 plus its subdirectories, and a `..` chain that never reaches the root. Repair points a wrong `..` at the directory that names it and reports the rest.
- `-preflight` warns when a broadcast port or the API port is in the NodePort range 30000-32767 on a host that looks like a Kubernetes node.

### Changed

- Writes handle contiguous blocks as one run instead of block by block. An overwrite of blocks one extent maps takes one in-place check, one extent lock per megabyte and one device write; new blocks that follow each other on the device are written together; and a first write into `fallocate`d blocks clears the whole range it covers at once. At 8 KB blocks, a 512 MB overwrite with 128 KB writes went from 57 to 257 MB/s on a tmpfs-backed volume, the same as at 1 MB, and writing into a `fallocate`d 512 MB file from 43 to 456 MB/s.
- `goclusterfs-fsck` tracks blocks in a bitset and one byte per block instead of maps. On a 100 GB volume at 8 KB blocks with 90 GB allocated, a check takes 3.2 s and 39 MB of memory instead of 23 s and 1.6 GB.
- `statfs` (`df`) no longer reads the whole inode table on every call. It returns a free-inode count that this node's creates and removes adjust at once, and that a background scan refreshes once it is older than 30 times the last scan took, at least a second. Other nodes' creates and removes show up late by that much. At 16 KB per inode the table of a 100 GB volume is 1.6 GB. `statfs` also reads the block bitmap 1 MB at a time instead of 4 KB.
- `-block-reserve` defaults to 64 MB of blocks instead of 64 blocks: 64 at 1 MB, 8192 at 8 KB. Pass a number of blocks to choose another size, as before.
- `fallocate` finds the holes in its range in one pass over the file's extents, instead of two lookups per block, and removing or truncating a file frees its blocks in batches of 1,048,576 instead of listing them all at once.
- File data goes to the device in one I/O per contiguous span instead of one per 4 KB sector. A 1 MB read or write of one block was 256 device I/Os and is now 1; a write that covers part of a sector at either end first reads only those sectors. On an iSCSI LUN in the VM test setup, fio 1 MB sequential O_DIRECT writes went from 16 to 55 MB/s and reads from 18 to 100 MB/s; the raw LUN does 129 and 143.
- A create no longer rereads the used part of the inode table to find a free inode. Before, every create read every used inode from the node's start: 12 MB per create with 44,000 files on the volume, and more as files accumulate. Each node now resumes its search after the last free inode it found. An inode the node frees moves the search back, so it still reuses inodes from its own part of the table first. When a peer frees a file this node unlinked, this node's next orphan pass moves the search back to it. Once a minute the search starts over from the node's start, so inodes other nodes free are reused too. Copying a 44,000-entry node_modules tree onto a tmpfs-backed volume now reads 0.8 MB per entry instead of 6.9 MB, and runs at 436 entries/s instead of 274.
- `goclusterfs-fsck` reads the inode table 1 MB at a time instead of one 4 KB sector per read. Phases 3, 4 and 6 each read the whole table in 4 KB pieces, so reads grew with volume size, and phase 8 reread one sector for every file to check its link count. On a 150 GB volume with 100,000 files, a check now makes 3,900 reads instead of 133,000, and takes 6.5 s instead of 90 s over iSCSI in the VM test setup, and 1.5 s instead of 38 s on a local file. When a 1 MB read fails, fsck reads its sectors one at a time, so it still reports only the unreadable sector.
- The snapshot registry is read in one 1 MB I/O instead of 256 reads of 4 KB, so listing snapshots (`getfattr -n user.snapshots`, the API) and creating, finding or changing one no longer cost a disk round trip per registry sector. A sector whose checksum fails in that read, as one a peer was writing, is read again on its own as before. With 860 snapshots on a loaded ext4 disk, a listing went from 52 ms to 3.4 ms and a snapshot create from 90 ms to 3.6 ms.
- A node whose replay of a crashed peer's journal fails 3 times in a row with the same error now retries every 10 minutes instead of every minute, logs the failure at most once an hour, and reports `/health` `recovery` as degraded with the slot and a `goclusterfs-fsck -inspect-slot` hint until a replay succeeds or the slot changes hands. Lock timeouts do not count.
- Freeing blocks that no snapshot or clone shares takes only the block bitmap lock, once per operation, not the refcount lock and one bitmap lock per block. Snapshots and clones take the bitmap lock while they count a file's blocks.
- Each node keeps the directories it reads in an in-memory index, so a lookup no longer reads and decodes the whole directory. A lookup checks the directory inode's generation on disk before it uses the index, so other nodes' changes show on the next lookup without broadcast. Removing an entry now writes the directory inode before the child is freed. `-dir-index-entries` caps the names held (default 1,048,576, about 100 MB), and `/metrics` counts hits, misses and rebuilds. In one test with two nodes, `ls -l` of 4,000 files went from 65 s to 1 s, a `stat` from 3.8 ms to 0.25 ms, and a create from 14 ms to 6 ms.
- `-format` now writes a superblock with the volume layout and zeroes all metadata regions, even on a device that already holds a filesystem. Mount reads every region offset from the superblock.
- At most 64 nodes mount a volume at once, one per node registry slot.
- Moved the FUSE library from `bazil.org/fuse` to `hanwen/go-fuse` v2.
- `go.mod` now requires Go 1.26.
- `make build` builds `goclusterfs-fsck` as well as `goclusterfs-mount`.
- `make test-integration` now allows 30 minutes, since the full suite takes about 15.
- Mount no longer creates an SFB manager, which nothing used, and logs that SFB is disabled instead of `SFB: enabled`.
- FUSE read and write requests carry up to 1 MB, up from 128 KB, and readahead is 1 MB.
- Reads use the inode cache, a node keeps a released lock for 10 ms so back-to-back operations take it again without disk I/O and yields a lock it has reused for 250 ms, and the inode and extent caches are split into 16 shards.

### Removed

- `cmd/crctest`, a development tool that printed two CRC32C values. `internal/storage`'s `TestCRC32C` already checks both, and releases never shipped it.
- The legacy single-block prototype in the repository root (`main.go`).
- The journal's `FullThreshold` setting, which nothing read. A checkpoint still runs every 5 seconds and when a transaction does not fit.

### Fixed

- The reservation check a fenced mount runs every 5 seconds warned `checking the device's reservation failed: resource temporarily unavailable` when it ran while a dm-multipath map was suspended, as when multipath reloads its table after a path logs out and in. It now tries again twice, 250 ms apart, before it warns.
- A node killed while it held a lock, then a mount of it refused before its replay, left the killed node's lock claims under the refused mount's registry slot. A peer's replay of that slot did not take them over and waited for itself: on a lock it needed, such as the block bitmap's when it frees the crashed node's unused reserved blocks, for a minute or without end, and the survivor's reads of the crashed node's files failed with EIO meanwhile. A replay now takes over every claim in the slot it replays.
- On targets that answer a preempted host's next commands with more than one unit attention, as TrueNAS SCALE 25.10 does where LIO answers one, a fenced node's reservation commands failed with `status 0x2` instead of reporting it fenced, and `goclusterfs-fsck -test-reservations` failed its two-host test. A command that gets status 0x2 is now sent again up to 5 times. The self-test lists each unit attention it saw, with its sense code.
- On an LIO target, a node could not be fenced after an iSCSI logout and login of its host. LIO keeps a registration under the session that made it, and while one of a host's registrations holds the reservation, it lets every session of that host write. A clean unmount after the relogin found no key on its session and left the earlier one, which kept the reservation. When a later mount on that host stalled and a peer revoked its key, its queued writes still landed after the peer took over. A clean unmount now removes the key from the earlier session too.
- A clean unmount left the node's registry slot marked active, for a running node to clear about 20 seconds later. After every node of a cluster unmounted cleanly, no node was left to clear the slots, so the first node to mount a volume without fencing again was refused as if those nodes were mounted. A clean unmount now empties its slot once its journal stopped cleanly. A slot that still lists files unlinked while open, or whose journal did not stop cleanly, stays active for a peer to recover.
- A mount whose host's earlier mount in the same slot had exited, but was still a zombie its parent had not reaped, took that slot for a running node. A remount then took another slot and left its own journal for a peer to replay, and on a volume without fencing it refused to mount next to itself. In a container whose init does not reap, the zombie lasts for good. A zombie now counts as exited.
- Create, mkdir and chmod dropped the setuid, setgid and sticky bits, and stat never showed them. A new file in a setgid directory took its creator's group instead of the directory's.
- A new mount on the same host judged another mount's heartbeat by the wall clock, so a forward clock step of 20 seconds or more made a live mount look dead: the new mount took its registry slot and, on a fenced volume, revoked its access. A mount now takes a slot whose process it cannot prove exited only after watching the heartbeat stay unchanged for about 20 seconds, as for other hosts' slots. A restarted container whose peers keep running may now see a peer replay its old slot first, and then takes another slot.
- A write that hit a read error when it re-read its inode, after taking the inode lock or after moving a small file out of its SFB slot, crashed the mount with a nil pointer panic. It now fails with EIO.
- A mount rolled back every snapshot still being created, including one a live node was creating at that moment, and that node's snapshot failed with EIO. A snapshot now records the registry slot and node UUID of the node creating it. A mount rolls it back only when that slot is empty or another node holds it. A dead node's half-made snapshots are rolled back by the node that replays its journal, after the replay. A snapshot that another node rolls back anyway fails with EAGAIN, and you can retry it.
- Failure detection handed each peer's orphan list to the filesystem before it checked heartbeats, and the filesystem could wait there for a lock the dead peer held. A node that died with orphaned files held up its own replay: peers' requests for its locks waited 30 seconds and failed with EIO, and one wait could stop failure detection for good. Orphan lists now go through a loop of their own that skips a failed peer, whose replay adopts its list. Lock requests also judge a peer's slot by the last read any check made, so a dead peer stops looking alive while other checks keep reading its slot. Unmount no longer waits for an orphan pass stuck on a lock.
- A file operation that needed a lock held by a node that had just failed, while it held another lock, gave up after 30 seconds with EIO. Detecting the failure and replaying the node's journal can take longer than that. When the replay needed a lock the waiting operation held, as a dead node's unlink in the same directory does, the operation had to give up before the replay could finish. Unlink, rmdir, create, mkdir, rename, link, symlink, setattr and the snapshot and clone paths now let go of their locks at once, wait for the replay, and retry, so they no longer fail. If the replay keeps failing, they wait until an admin releases the slot. A rename takes its directories' inode table sector locks before its journal commit, so it never waits for a lock after it.
- A block free that gave up waiting for the bitmap or refcount lock, after the 30-second limit, left the blocks allocated with no file mapping them until `goclusterfs-fsck -repair`. The node now keeps them queued, logs a warning, and frees them with its next free and once more at unmount, where it logs how many are still left, if any.
- Journal replay skipped an entry whose op type it did not know, so a node replaying a journal that a newer build wrote would apply the rest of that operation without it. Replay, by the node itself or by a peer, now stops at that transaction before any of its entries apply, and refuses a journal whose header names a newer format version. The slot stays for an admin; `goclusterfs-fsck -inspect-slot N` shows `cannot replay: unknown op 0x...`.
- A snapshot of a file that lost its last name while a node still had it open was not an orphan until every node closed the file: the API listing did not mark it, and `DELETE /api/v1/snapshots/<name>` without `path` answered 409 and said to delete it through a file that had no name. Such a snapshot is now an orphan as soon as the file's link count reaches 0. Deleting it leaves the open file's data alone.
- A node paused between reading its registry slot and writing its heartbeat could resume after another node had replayed it and emptied the slot, write the slot back as its own and keep running, so two nodes wrote as the same owner. A node now stops without writing when it went more than 15 seconds without a heartbeat, stops when a heartbeat write completes that late, and its write gate refuses writes after such a gap without trusting a read of the slot. Shorter stalls, such as a storage path failover, still do not stop a node. The gap counts time the host spent suspended and ignores wall clock steps. A new mount on the same host, a restarted container, a rebooted host, `-skip-recovery` and a mount that finds no empty slot now take a live-looking node's slot only after its heartbeat stopped for about 20 seconds, as running nodes do, instead of 10 to 12 seconds, so they no longer take the slot of a node that stalled for less than 15 seconds.
- Journal replay narrowed a logged 64-bit inode number to 32 bits, so a damaged record naming inode 2^32+2 acted on inode 2, the root directory, instead of failing. Replay now refuses a record that names an inode at or past the end of the inode table, before it changes anything. The replay of that journal then fails like any damaged journal: list it with `goclusterfs-fsck -inspect-slot N` and free the slot with `-release-slot N -salvage`, as OPERATIONS.md's Damaged Journal Slot describes. `goclusterfs-fsck -inspect-slot` and salvage reports also decode hard-link records, which they reported as undecodable.
- A write that passed the stalled-node check could then wait for another write to the same 1 MB region and land after other nodes had declared its node dead. Each write now checks again once it holds its locks, right before it reaches the device. A stall in that last step can still let a write through; only storage fencing closes that.
- A directory entry naming an inode at or past the end of the inode table, which only on-disk damage produces, wrapped its 64-bit number onto a real inode: a lookup of an entry naming inode 2^32+2 returned a regular file backed by the root directory's inode. Lookup, unlink, rename and the API's path lookup now fail with EIO and log the entry once per directory and name; `goclusterfs-fsck` reports it.
- A node could give up a lock that no other node wanted and then wait 50 ms to take it back. It checked its row for waiters, found none and started a new turn, then checked the clock again; when the turn ran out between the two checks, or the node stalled there, it ended the turn anyway. It now gives the lock up only when the row shows another node waiting.
- On slow storage, a node in a low registry slot that kept using a lock shut out nodes in higher slots: after each turn it waited a fixed 50 ms and claimed the lock again before their slower claims finished, and a lower slot wins a tie. Readers on other nodes got one read in a test window while one node wrote. A node now leaves the lock alone after its turn until the waiting nodes have taken it, for at most one turn.
- `goclusterfs-fsck -release-slot` left the released node's lock claims in place. A node that later registered in that slot made them count as its own until its mount finished its own journal replay, so peers waited on those lock records meanwhile. The release now clears them.
- A mount with `-journal=false` skipped replaying the journal its registry slot held from a crash, so a later mount with the journal on replayed those old transactions over newer writes; with `-skip-recovery` it logged that it discarded the journal but left it in place. It now replays the slot's journal whatever `-journal` says, and `-skip-recovery` resets it.
- A journal header whose state was corrupt or a value this build does not know counted as clean, so a mount would start a new journal over it and peers would skip it. Replay now refuses it with `journal is corrupt`.
- `goclusterfs-fsck -release-slot` emptied the slot's list of files its node had unlinked while they were open, so those inodes leaked until `goclusterfs-fsck -repair`. The released slot now keeps the list: live nodes free those files once no node has them open, and the next node to use the slot takes the list over.
- A write error partway through a rename, after its journal commit, could leave the file or directory under both names or neither, and the rename ended its intent, so replay never fixed it. The rename now redoes the missing writes while it still holds its locks. If that fails too, the node stops and keeps its locks, so replay finishes the rename before another node can change those directories.
- When a journal commit failed after its record reached the journal, the next commit could make replay run the failed operation anyway: a create the caller was told failed could take an inode a later create had reused, giving one inode two names. A failed commit now ends its record.
- An API snapshot or clone could hang the mount daemon while files were being written: the API opened the file and called `setxattr` through the daemon's own FUSE mount, so the daemon waited on the kernel while the kernel waited on the daemon. The heartbeat stopped, the node lost its registry slot, and the process stayed a zombie. The API now runs those requests inside the daemon and only notifies the kernel's caches afterwards, in the background.
- The HTTP API answered a path no endpoint matched, such as `/api/v1%2F` with an escaped slash, with a plain-text 404. It now answers with the same JSON error body as every other API error.
- `goclusterfs-fsck` never checked a directory's `.` entry. It now reports a missing `.` or one that names another inode, with both inode numbers. `-repair` points a wrong `.` back at the directory and a wrong `..` at the directory that names it, found by walking the names down from the root, for example after a crash in the middle of a rename that moves a directory.
- A power failure or an I/O error during mkdir or rmdir could leave the parent directory's link count off by one: the entry and the count were written under separate locks, and replay did not fix the count. Both now change in one write of the parent's inode. Replay, or the failed mkdir or rmdir itself, then sets the parent's count from its subdirectories.
- `goclusterfs-fsck` checked a directory entry's type only when the entry's inode number was below the count of inodes in use, and then only that the type was a valid value. It now reports every entry whose type differs from its inode's, which lookup, unlink and rmdir trust: an unlink could remove a directory that its entry calls a file. It also reports an entry whose inode number is past the inode table; before, a number past 2^32 wrapped and could pass as an inode in use.
- `goclusterfs-fsck` never checked a snapshot's parent: the check was an empty block. It now warns about a snapshot whose parent snapshot does not exist, is the snapshot itself, or was taken of another file. Deleting a snapshot hands its children to its parent.
- A file node that outlived its file, such as an O_PATH descriptor or a name another node had just removed, could open, read, write and truncate the next file to take its inode slot. It now fails with ESTALE.
- Snapshot lookups and listings skipped a snapshot registry sector they could not read: `getfattr -n user.snapshots` and `GET /api/v1/snapshots` returned part of the list, and a delete, clone or lookup of a snapshot in that sector reported it missing. A snapshot delete job took such a snapshot for already deleted. They now fail with `EIO`, and the API answers 500 with the sector and what to run. A snapshot in a readable sector is still found, and mount still succeeds and logs a warning naming the sector.
- A file unlinked while open, on this node or another, was freed at once: its descriptors read and wrote whatever file took the inode next. The file now keeps its inode and blocks until every node has closed it. A node that dies holding it lets go when a peer replays its journal. While other nodes are mounted, each node tracks up to 487 unlinked files that other nodes have not yet let go of. An unlink beyond that waits, and fails with EBUSY only when live nodes keep holding them for 20 s.
- Opening or stat-ing a file that another caller had just unlinked failed with EISDIR, or showed the freed inode's empty attributes. It now fails with ESTALE, and the kernel looks the name up again.
- An open with O_CREAT and no O_EXCL failed with EEXIST when another node or thread created the same name between the kernel's lookup and the create. It now opens that file, and truncates it with O_TRUNC.
- Reads no longer show bytes nobody wrote to the file. A partial write into a newly allocated block left the rest of that block as the disk held it, often a deleted file's data, readable as soon as the file covered it. A truncate into the middle of a block left the old bytes after the cut, and growing the file later showed them. A first write into a block now zeroes the parts of it below the end of the file that it does not cover, and a write, truncate or fallocate that grows the file zeroes the rest of its old last block first, copying it if a snapshot or clone shares it. Sequential writes write their data once.
- A damaged block reserve record in a journal could make journal replay and `goclusterfs-fsck` allocate up to 32 GB. A reserve record now holds at most 1,048,576 blocks, and a larger `-block-reserve` acts as 1,048,576.
- A damaged journal record that claimed a length within 4 KB of 4 GB crashed journal recovery with a panic. Recovery now treats it as corrupt.
- A node registry slot with a zero checksum was accepted whatever it held, so a slot torn or zeroed at its end read as valid. Now only an all-zero slot, which no node has written, skips the checksum.
- A damaged directory entry whose name ran past the end of its record was read with bytes of the next entry as part of its name. It is now rejected as invalid.
- Deleting or rewriting a file that an older build stored in an SFB slot crashed the mount when the container header was damaged so the slot lay past its bitmap. The slot is now left allocated.
- `goclusterfs-fsck` ran for hours on a superblock with a damaged node count, reading one journal per node it claimed. It now reads at most the 64 that the node registry has.
- One failed write while a node released a lock left its claim on the device, and the node forgot it: other nodes timed out with `EIO` on every resource in that lock record until the node unmounted. The node now clears such a claim again every second until the write succeeds.
- One failed read of the snapshot registry during a snapshot create could delete other snapshots: the create counted the unreadable sector's slots as free, and a write to a sector it could not read replaced the sector with one that held only the new snapshot, losing up to 30 others. The create still reported success. Both now fail with `EIO` and leave the sector alone. A sector that stays unreadable now blocks every snapshot create. `goclusterfs-fsck -repair` rewrites one that fails its checksum: it keeps the snapshots whose descriptors pass their own checksum and reports each one it clears. A sector the device cannot read stays as it is.
- Nodes judged each other's heartbeats and recovery leases by wall clock. A node mounting with its clock more than 10 seconds ahead took a live node's registry slot and stopped it; a crashed node whose clock ran ahead was replayed only once its clock's lead ran out; and a replay whose node's clock was behind looked abandoned, so lock waits for the dead node failed with `EIO`. A node now counts another as failing, dead or abandoned only after reading the same heartbeat or lease for long enough by its own clock; a mount takes another host's slot only when it held that hostname before a reboot, when `-skip-recovery` names it, or when no slot is empty, and only after watching its heartbeat stay unchanged for about 20 seconds.
- Under slow storage a node was declared dead while it was only slow: registry scans held the heartbeat back for 64 reads each, so at 1 second per I/O a peer replayed the node and it stopped. Scans now read the registry in one I/O without holding the heartbeat's lock, and registry I/O no longer waits for other I/O to the same 1 MB region.
- A node in a higher registry slot could wait 30 seconds and fail with `EIO` for a lock that a node in a lower slot kept releasing and claiming again every few milliseconds. A node that loses a claim to a lower slot now leaves a waiting mark in its own slot, and the holder gives the lock up 250 ms after it first sees a live node's mark.
- `chmod`, `chown` and `touch` could undo another node's concurrent change to the same inode: on a directory, a create's link count or mtime; on a file, the size an append inside an allocated block set. Directory attribute changes now hold the inode lock from read to write, and file attribute changes retry when the inode changed since they read it.
- After 3 failed multicast sends in total, counted over the whole mount, a node sent cache invalidations only to unicast peers until it unmounted. Now only failures in a row count: a successful send resets them, and after 3 in a row the node tries multicast again 30 seconds later.
- `chmod` cleared a file's type bits, so the file could no longer be opened ("Is a directory") and fsck reported an invalid file type. `chmod`, `chown` and `touch` now also work on directories and the mount root, which returned "Operation not supported".
- The cache summary logged at unmount showed hit rates 100 times too high.
- All nodes wrote the same journal region. A restarting node replayed and then reset the journal of nodes still writing, and no node could replay a crashed node's journal. Each node registry slot now owns a 4 MB journal, and a crashed node's journal is replayed through its slot.
- Nodes never sent registry heartbeats, so a node mounting more than 10 seconds after another took the live node's registry slot.
- After a partial write into a fallocated range, reads of the other fallocated blocks, and of the rest of the written block, returned old disk contents. They now return zeros.
- Snapshots and clones never copied on write: block refcounts stopped at 1, so a snapshot kept nothing and a write to a clone changed its source. Each snapshot now keeps the blocks it captured in a hidden inode, a write to a shared block copies it first, and a block is freed only when its last owner lets go.
- Deleting a snapshot after its file changed failed with a refcount underflow and left the snapshot deleting forever, because the delete used the file's current blocks.
- A snapshot or clone could undo another node's change to the source file made while the file was being marked shared, such as the new size after an append, a chmod, or new times. The mark now holds the inode lock from its read to its write.
- Two delete jobs for one snapshot, from a double delete or a node mounting while another node deleted it, could empty the data of a new snapshot that took the freed inode slot. A delete job now empties a data inode only while the snapshot still names it, and a job that finds the snapshot already deleted succeeds.
- Writes failed with `EAGAIN` once a file needed a third extent, so most files over 2 MB could not be written. Extents past the first two now go in an on-disk extent tree, and adjacent extents merge.
- `goclusterfs-fsck` phase 4 never checked file extents, because it read inodes into unaligned buffers that `O_DIRECT` rejects.
- A node could serve a stale cached inode after another node freed and reused its inode number. Inode generations now survive free and reuse, and opening a file reloads its inode from disk.
- Journal recovery no longer panics, loops forever, or allocates gigabytes on a corrupt journal. It now rejects short entries and bad ring geometry as corrupt.
- Lock-order violations when several nodes create files and directories at the same time.
- Two nodes could each hold a lock and wait for the other's, then fail with `EIO` after 30 seconds, when a write's inode and block locks mapped to records the other node held. Each lock type now has its own lock records.
- Inode allocation races between nodes; allocation now retries with jittered backoff.
- Directory operations now update caches and send broadcast invalidations.
- The broadcast peer table never dropped an entry: every remount and every forged heartbeat added one. Peers are now kept by address, at most `-broadcast-max-peers` of them, and so are the nodes whose message numbers a node tracks.
- A cache that kept evicting entries grew in memory past its limit, because a Go map keeps the room of deleted keys: the extent cache took 5.8 MB when full and 10.9 MB after 40 times its size went through it. Each cache shard now rebuilds its map after it has evicted as many entries as it holds.
- A file held open on one node could return short reads for up to 9 seconds after another node grew it, when that node's broadcast messages did not arrive. `stat` read the new size from disk, but reads used the cached inode until `-cache-ttl` passed, and while the other node kept writing the two kept disagreeing. Getting a file's attributes now refreshes the cached inode too, so open files catch up within about twice `-attr-timeout`.
- A read right after `open` could stop early when this node's kernel had cached the file's size during another node's write, for example from a desktop volume monitor or `ls -l` scanning the mount. Opening a file now makes the kernel fetch its size again.
- A node that lost broadcast invalidations, for example when its receive buffer filled during a burst of writes on another node, kept stale inodes until `-cache-ttl` and logged nothing. It now sees the gap in the sender's sequence numbers, drops its inode and extent caches, and logs it at most every 10 seconds. The unmount stats line reports `lost=N`.
- Broadcast deduplication kept every message for 5 minutes: about 224 MB per 2.4 million messages, and cleaning it up held up message handling for up to 200 ms. It now keeps a 64-message window per sender.
- Docker and VM test suites now run on fresh hosts.
- The README quick start now uses the real binary names and flags.
- Create, mkdir, clone and snapshot failed with "No space left on device" when the lock wait for the new inode gave up or its slot could not be read. They now fail with `EIO`. `ENOSPC` means the inode table is full.
- Writes and fallocate failed with "No space left on device" when the lock wait for the block bitmap gave up or a bitmap sector could not be read. They now fail with `EIO`. `ENOSPC` means no free blocks are left or the backing storage is full.
- Directory entries went only into the first 4 KB of each 1 MB directory block, so a block held about 250 short names or 15 long ones, and a busy directory took a new block every few creates. Entries now fill the whole block. A lookup reads each block in one I/O, and an add or remove writes only the 4 KB it changed.
- A node that other nodes declared dead while it was stalled, for example a paused VM, kept writing when it resumed. A node now checks before every device write that it still owns its registry slot, and refuses the write and exits if it does not. A write it started before the stall can still land.
- A node stalled for 15 seconds while it held a lock, for example a paused VM, lost the lock to other nodes, which could then write the same metadata. Other nodes now wait for a failed node's locks until it is proven dead and its journal is replayed, with no time limit, and give up only if the replay fails or is abandoned, or after 30 seconds if the waiting operation already holds another lock the replay may need. An overwrite of existing file data instead lets go of its locks and retries, so it does not fail. Failure detection now replays only nodes proven dead.
- A mount that took the registry slot of a failed node on another host did not keep that node's locks while it replayed the node's journal.
- Two nodes replaying dead nodes whose locks shared a record waited on each other until the lock timeout.
- A failed journal replay of a dead node still freed that node's locks, so other nodes could use half-replayed metadata until the retry a minute later. The locks now stay held until a replay succeeds.
- A mount whose own journal replay gave up waiting for another node's lock exited at once. It now retries with backoff and logs the holder; any other replay failure still fails the mount.
- Replaying a failed node's journal could overwrite an inode change that the replaying node made after the replay read the inode, such as a `chmod` or an append. The replay now writes the inode only if nothing wrote it since the read, and otherwise skips that record.
